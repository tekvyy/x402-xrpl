# AGENTS.md — Reusable conventions for the XRPL x402 Gateway monorepo

- Monorepo: pnpm workspaces, `packages/*`, each package `@app/<name>` with `"type": "module"`.
- TypeScript: every package `tsconfig.json` extends root `tsconfig.base.json` (NodeNext, strict, `verbatimModuleSyntax`). Relative imports MUST use `.js` extensions.
- Shared contracts live ONLY in `packages/shared` (enums, constants, env, zod x402 schemas). Never redefine enums or use bare string literals for domain concepts — import from `@app/shared`.
- Enums are the source of truth. Postgres enum types in `migrations/` mirror `packages/shared/src/enums.ts` — keep them in lockstep.
- Config: use `loadEnv()` from `@app/shared`; it throws an aggregated error on missing keys. Add new keys to both `env.ts` and `.env.example`.
- Migrations: `migrations/<numeric>_name.sql`, node-pg-migrate SQL format with `-- Up Migration` / `-- Down Migration`. Run `pnpm migrate:up` / `pnpm migrate:down`.
- Every gateway-submitted XRPL tx must carry the configured `SOURCE_TAG` (inject centrally in the XRPL service).
- Verify commands: `pnpm -r build`, `pnpm -r typecheck`. No local Postgres/Docker in this env — validate migration SQL with `@electric-sql/pglite` (install as throwaway, remove after).
- Runtime verification without live infra: build, then run a throwaway `.mjs` against `packages/*/dist` with in-memory stubs (a `pool` whose `query`/`connect` match on SQL prefixes, stub `redis`, and a fake XRPL via `Object.create(XrplService.prototype)` overriding `getTransaction`). Use `fastify.inject()` for routes and `.listen()` for a real origin. Delete the script after.
- Gateway architecture: routes (`routes/*.route.ts`) are thin; logic lives in `services/*` and data access in `db/repositories.ts` (every repo fn takes an explicit `Queryable` so it works inside a pooled-client transaction). Deps are injected via `GatewayDeps` (no module singletons); `server.ts` is the sole composition root.
- Pay-per-call verification is one shared fn `verifyPayPerCall` (side-effect-free); `settle`/`verify` in `settle.service.ts` reuse it. Single-use nonce is enforced by an atomic `UPDATE challenges SET status WHERE status = ANY(allowed)` guard, not an app-level check.
- On-ledger amounts: store/compare human units in DB; the x402 wire `amount` is drops for XRP (via `xrpToDrops`) and human units for RLUSD. Compare decimals with `util/decimal.ts` (scaled BigInt), never `Number`. RLUSD on-ledger currency is the 40-hex form (`XrplService.rlusdCurrency()`), not the 3-char code.
- PayChan credits are XRP-only (native). Claim crypto: client `signPaymentChannelClaim(channelId, XRP-decimal, privateKey)`, gateway `verifyPaymentChannelClaim(channelId, XRP-decimal, sig, pubkey)` — both take XRP decimal (NOT drops); the wire `cumulativeAmount` stays drops, convert at the crypto boundary. Avoid `authorizeChannel` (it takes drops → mismatch). Channel signing pubkey and deposit are read from the ledger (`XrplService.getPaymentChannel`, `ledger_entry` + `payment_channel`), never trusted from the client. Monotonic / within-deposit / covers-price is one atomic guarded `UPDATE channels ... WHERE credits_used < $new AND $new <= credits_total AND ($new - credits_used) >= price` (`applyChannelClaim`), not app-level checks. Per-call credit spend writes a `usage_events` row (tx_hash null, drives the live feed); the on-chain `PaymentChannelClaim` redeem writes the `payments` row — split to avoid double-counting revenue.
- xrpl.js does not export the `PayChannel` ledger-entry type at top level — define a local interface for the fields you read. `isCreatedNode` + `CreatedNode.LedgerIndex` (LedgerEntryType 'PayChannel') gives the channel id from a `PaymentChannelCreate` tx's meta.
- Live dashboard feed: every `usage_events` insert is published to a per-seller Redis channel (`usageChannelName` in `usage.service.ts`) AFTER the DB `COMMIT` (capture the returned row, publish outside the tx) so the dashboard never sees a rolled-back event. SSE routes use `reply.hijack()` then write to `reply.raw` (never return a value, or Fastify double-sends); set `Access-Control-Allow-Origin` manually since `writeHead` bypasses the cors plugin; use a dedicated `deps.redis.duplicate()` subscriber (ioredis subscribe mode is exclusive) and `quit()` it on socket `close`. SSE keep-alive lines start with `:`.
- Postgres aggregates: cast `COUNT(...)::int` to get JS numbers (raw COUNT is a string), and `COALESCE(SUM(numeric), 0)::text` for money sums (keeps precision, handles empty groups). Amounts stay strings end-to-end; compare with `util/decimal.ts`, never `Number`.
- Facilitator HTTP surface (`routes/facilitator.route.ts`): `POST /challenge` (issue a single-use nonce for a registered seller) + `POST /settle` (verify+consume) + `POST /verify` (no-consume, in `usage.route.ts`). These are thin wrappers over the existing `issueChallenge`/`settle`/`verify` services — never re-implement x402 logic in a route.
- Server middleware (`@app/sdk-server`) is DELEGATION, not duplication: it has NO XRPL/verify code. Split the middleware into a framework-neutral `core.ts` `decide()` (no-header → POST gateway `/challenge`, answer 402; header → POST gateway `/settle`, on SETTLED attach `X-PAYMENT-RESPONSE` and proceed) plus thin Express/Fastify adapters that only translate the `X402Decision` into their own req/res. Pricing lives in the gateway seller registration (single source of truth); middleware config is just `{ gatewayUrl, sellerId }`, NOT `{ price, asset, payTo }` (that would duplicate). express/fastify are optional peer deps (type-only imports, so no runtime coupling).
- Agent tool (`@app/agent-demo`): wrap `x402fetch` as an MCP-style descriptor (`{ name, description, inputSchema (zod), invoke }`) — self-contained, no MCP SDK dep needed. The credits path vs pay-per-call is chosen purely by whether the `X402Config` carries a `channel`; reuse the same tool factory for both.
- Cross-package runtime smoke that spans packages not linked at repo root (e.g. gateway + sdk-server + agent-demo together): import from RELATIVE `./packages/*/dist/index.js` (bare `@app/*` only resolves inside a package that depends on it), and load third-party deps like `fastify` via `createRequire(new URL('./packages/gateway/package.json', import.meta.url))`. Route middleware HTTP calls into a real `buildApp` via an inject-as-fetch shim (`app.inject` → `{ ok, status, json, text }`).
